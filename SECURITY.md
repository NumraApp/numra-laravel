# Security policy

`numra/laravel` mounts a route in front of a credential that reads a shared
fraud ledger and spends a merchant's paid quota. A weakness in it is worth
something to the people the ledger exists to describe, so please treat one
accordingly.

## Supported versions

| Version | Supported |
|---|---|
| 1.0.x | Yes |

1.0.0 is the first public release, so there is nothing older to support. When
a later major line opens, this table will say how long 1.x keeps receiving
security fixes.

## Reporting a vulnerability

Mail **security@numra.ma**. Put the package name in the subject.

**Do not open a public issue, pull request or discussion for a security
problem.** A public report is a working exploit for every merchant running the
released version until a fix ships, and the fix takes longer than the reading.

Useful to include:

- the package version, the Laravel version and the PHP version;
- what an attacker can do, and what they need in order to do it;
- the smallest reproduction you can manage.

Please do not send a live API key, a webhook secret, or a real customer's
phone number. A rotated test key and an invented number make the same point.

## What to expect

- An acknowledgement within three working days.
- An assessment, and either a fix or an explanation of why we do not consider
  it one, within ten working days.
- A fixed release, an entry in [CHANGELOG.md](CHANGELOG.md), and a published
  advisory once merchants have had a chance to upgrade.
- Credit under whatever name you want, or none.

We will ask you to hold public disclosure until the fixed release is out. We
will not ask you to hold it indefinitely.

## In scope

Anything that reaches `numra.check` or `numra.outcome` without satisfying the
configured rule — a closure, a Gate ability, or the `auth` shorthand; anything
that makes an undefined or misspelled ability allow rather than deny; anything
that puts `NUMRA_API_KEY` or `NUMRA_WEBHOOK_SECRET` into a response, a log line
or an exception message; anything that defeats or weakens webhook signature
verification, including the replay window.

Also in scope: the route macro mounting anything the merchant did not ask for,
middleware passed to the macro replacing rather than appending, and the
webhook route being reachable in a way that was not intended to be outside
CSRF and the throttle.

## Out of scope

Findings that require a merchant to have already published their own API key,
`NUMRA_AUTHORIZE=auth` being too weak for a public checkout — the README says
so and the choice is the merchant's — missing hardening headers on the
surrounding application, and reports generated by a scanner without a
reproduction.

If the finding is in the client rather than in the Laravel wiring, it belongs
to [numra-php](https://github.com/NumraApp/numra-php) — mail it to the same
address either way, and open a public issue in neither.
